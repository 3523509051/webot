# 上下文与记忆设计

> 以**当前代码实际行为**为准。最后同步：2026-10-07

---

## 1. 为什么必须自研（核心事实）

**AstrBot 原生只把「被 @ 的那条消息」送进 LLM，未 @ 的群消息根本不进上下文。**

后果：群里聊了 20 条在讨论一个 bug，最后有人 `@机器人 你看看` —— 机器人**只看到这一句**，
完全不知道"这个"是什么。

所以记忆层必须自己接管。这是本项目自研插件存在的**唯一理由**。

---

## 2. 四层记忆

| 层 | 是什么 | 谁实现 | 状态 |
|---|---|---|---|
| **L1** | 群聊滚动背景（最近 N 条群消息，含未 @ 的） | **自研**（`window.py`） | ✅ 已实现 |
| **L2** | 多轮对话历史（当前会话里谁说了什么、机器人回过什么） | **AstrBot 原生会话** | ✅ 复用原生 |
| **L3** | 按群隔离的**结构化群员画像**（性格 / 爱好 / 身份），**带时间戳** | **自研**（`memory.py`） | ✅ 已实现（v0.4.1） |
| **L4** | 按群隔离的**公共知识库**（梗 / 约定 / 共同经历 / 话题结论），语义检索 | **自研**（`kb.py`）+ AstrBot FAISS | ✅ 已实现（v0.6.0） |

**分工原则**：L1 补 AstrBot 缺的那一层（群聊语境）；L2 不重复造轮子（AstrBot 的会话管理本就够用）；
L3 管「人」、L4 管「事」—— 两者的取舍见 §5.1 与 §6。

## 3. L1 详解

### 3.1 记录

| 项 | 实现 |
|---|---|
| 时机 | `on_group_message` 内，在窗口判断**之前** —— 无论窗口开没开都在记 |
| 数据 | `{user: 昵称, text: 文本, ts: 时间戳, at: 是否 @ 了机器人}` |
| 容量 | 每群一个 `deque(maxlen=25)`，满则挤掉最旧 |
| 跳过 | 机器人自己发的消息；以 `/` 开头的命令 |
| 存活 | **内存态**，进程重启即丢失 |

### 3.2 注入

| 项 | 实现 |
|---|---|
| 钩子 | `@filter.on_llm_request()` |
| 条件 | `inject_l1` 且该群窗口**处于激活态**（窗口外不注入，省 token） |
| 位置 | `req.system_prompt += "\n\n" + 渲染结果` |
| 渲染格式 | 见下 |

```
# 群聊背景（仅供参考语境，不要把下面每一行都当成需要回复的问题）
小泽布尔: 今天那个接口又挂了   ← 在 @ 你
路人甲: 我看看
小泽布尔: 好像是超时
```

### 3.3 为什么注入时**去掉最后一条**

最后一条就是**当前这条消息**，它已经作为用户消息存在于请求里。
重复一次既浪费 token，也容易诱导模型把背景当成待回复的问题复读一遍。

（`/gactx` 命令查看的是**不去掉**的完整版本，便于调试。）

### 3.4 为什么注入 system prompt 而不是别处

现在的做法最简单，但**有一个已知的代价**（未修复）：

> prompt 缓存是**前缀匹配**的。L1 每次请求都在变（末尾追加），
> 会**使整个 system prompt 段落的缓存失效**，稳定的人设前缀也吃不到缓存价。

**更优做法**（待办）：把 L1 放进 `ProviderRequest.extra_user_content_parts`
（AstrBot 专门为"在用户消息后追加内容块"提供的字段），
让 system prompt 保持稳定 —— 人设前缀可命中缓存（价格约为未命中的 1/50）。

## 4. L2：AstrBot 原生会话

- AstrBot 为每个群维护一份 `Conversation`，多轮历史由它自己管理并做智能截断。
- 我们**不重复实现**，也不需要干预它的写入。

### 上限（2026-10-08 查证并调整）

AstrBot 默认 `agent_runner.config.compression.max_turns = -1`（**无条数上限**），
唯一刹车是估算 token 逼近 `max_context_tokens`（本项目配的是 1,000,000）时才触发
LLM 摘要压缩 —— 等于永不触发，历史会无限增长、每轮 token 越烧越多。

**当前策略（2026-10-08 二次调整）**：**不按条数截断**（`max_turns = -1`），
改为**接近 10 万 token 时压缩**：provider 的 `max_context_tokens = 122000`，
触发条件是「用满 82%」（`usage_rate > 0.82`）→ 实际约 **10 万 token** 触发
`llm_compress`：旧对话由 LLM 摘要成一段，近段保留 15%（`keep_recent_ratio`）。

- 为什么不用 40 条截断了：用户要「记得更久」，条数截断和 token 阈值二选一 ——
  留 40 条时 10 万阈值永远到不了。
- ⚠️ **代价**：单次请求 token 上限从 ~2k 级别升到可能 10 万（按量计费的模型上
  差 ~50 倍）。若目的是「防爆」而非「记更久」，建议改成 20000~30000 更划算。
- ⚠️ **前提**：`max_context_tokens` 被当作模型窗口用。若 DeepSeek 真实窗口小于
  10 万，压缩来不及触发就会报 context length 错误 —— 届时把 122000 调小即可。
- DB 里的原始历史不删（只是不再全量进请求），`/reset` 仍可彻底清。

### ⚠️ L2 会放大模型的坏习惯（真实事故：乱 @）

模型**会模仿自己历史里的写法**：2026-10-08 它在群里连续多条以「@如月之影 」开头，
之后不管谁发问都照抄这个开头（连对方说「艾特我」都能 @ 错人）—— 和 [PASS] 事故同源。
三道防线：① `/gareset` 一键重置本群 L2（新建会话，打断模仿）；
② `fix_mentions` 硬校正（回复里的 @ 只允许指向本条消息的发送者）；
③ 提示词写「要 @ 就写在开头、默认不用」。详见 `architecture.md` §4.1。

### 待决问题：休眠后要不要清空 L2？

早期决策是「**休眠后 L2 清空**」，但改用 AstrBot 原生会话后，这件事**尚未实现**，原因是：

- 清空需要调用 AstrBot 的会话管理 API（`context.conversation_manager`），
  需要先确认接口签名与副作用；
- 不清空的后果是：窗口关闭很久后再次 @ 它，它仍记得上一次的对话。

**当前行为：不清空**（沿用 AstrBot 原生语义）。等你定夺后再决定实现方式。

## 5. L3：结构化长期记忆（已实现，v0.4.1）

### 5.1 为什么不用向量库（知识库）

「某群员的性格爱好」有三个特征，恰好和语义检索的适用场景相反：

| 特征 | 向量检索（知识库） | 结构化 KV（L3） |
|---|---|---|
| 结构化（人 → 属性） | 靠语义相似，不擅长**按人精确查** | ✅ key 直接按人查 |
| 会变化（今天爱猫，明年未必） | 更新要重新嵌入，遗忘困难 | ✅ 覆盖 / 删除 |
| 必须按群隔离 | 需额外加 metadata 过滤 | ✅ key 就是群 id |

所以两者**互补而非替代**，而这个互补正好演变成了两个层：

- **知识库（向量）** → 外部资料 + **群公共知识**（梗 / 约定 / 共同经历）→ 这就是 **L4**（见 §6）
- **L3（KV）** → 「这个群里谁是谁、偏好什么」：人际记忆

### 5.2 存储

`data/plugin_data/astrbot_plugin_group_activation/long_term_memory.json`（容器挂载，重启不丢）

```json
{
  "<群id>": {
    "updated_at": "2026-10-07T20:30:00",
    "members": {
      "小泽布尔": {
        "updated_at": "...",
        "facts": [
          {"text": "喜欢调 AI、测机器人", "first_ts": "...", "last_ts": "...", "hits": 3}
        ]
      }
    }
  }
}
```

**每条事实都带时间**（按你的要求）：

| 字段 | 含义 |
|---|---|
| `first_ts` | 首次出现时间 |
| `last_ts` | 最近提及时间（用于排序与渲染） |
| `hits` | 被提及次数（重复出现 ＝ 更可信） |

写入用**原子替换**（临时文件 + `os.replace`），避免写一半损坏。

### 5.2.1 写入去重（v0.6.1 新增）

入库前对**本人已有事实**做语义去重（自算余弦、与 L4 同一套，阈值
`l3_dedup_score = 0.90`，同批新增之间也互相去重）。原因：`add_facts` 原本只按
**文本精确匹配**，换个说法就并存 —— 实测有「会自己搓工具并上传 GitHub」与
「会写代码，愿意分享到 GitHub」这类同义重复。嵌入失败时放行（宁可多记一条，
不因嵌入故障丢信息）。

### 5.3 提炼：何时、怎么

| 项 | 做法 |
|---|---|
| 触发 | 每次窗口活动都**重挂**一个延迟任务，`idle_seconds + 2` 秒后回看；窗口已休眠才提炼 |
| 为什么不监听 sleep 事件 | 窗口是**懒判定**的（只在有消息进来时才检查是否过期），群里没人说话就永远等不到那次检查 |
| 对延迟的影响 | **完全不影响回复延迟** —— 提炼跑在独立 asyncio task 里 |
| 三道闸门 | ① 窗口内新消息 ≥ `l3_min_new_messages`；② 距上次提炼 ≥ `l3_cooldown_seconds`；③ L1 非空 |
| 输入 | 当前 L1（最近 25 条）+ 提炼提示词 |
| 输出 | 严格 JSON `{"facts":[{"member","fact"}]}`，解析容忍代码块标记与多余文字 |
| 合并 | 文本归一化后相同 → 只更新 `last_ts` 并 `hits+1`；否则新增 |
| 容量 | 每人最多 `l3_facts_cap_per_member` 条，超出丢最久未提及的 |

提炼提示词**明确排除**：一次性内容（今天吃了什么）、机器人自己的人设设定、推测脑补。

### 5.4 注入

窗口激活时，把**本群**画像追加进 system_prompt：

```
# 你记得的这个群的人（长期记忆，仅供参考，不要逐条复述）
- 小泽布尔：喜欢调 AI、测机器人（10-07）；说话简短爱下指令（10-07）
```

- 最多 `l3_max_members` 人、每人 `l3_max_facts_per_member` 条
- 按「最近提及时间」排序，优先带最新的
- **与知识库的分工**：L4 知识库结果由**本插件**检索后放进 `system_prompt`（见 §6），
  L3 也走 `system_prompt`。AstrBot 原生的 `kb_agentic_mode` 工具式检索**不启用**
  （`kb_names=[]`），避免与 L4 重复注入。互不覆盖。

### 5.5 调试与清理

| 命令 | 作用 |
|---|---|
| `/gamem` | 查看本群长期记忆（含首见/最近时间与提及次数） |
| `/gaforget` | 清空本群长期记忆 |

### 5.6 局限

- 提炼依赖 LLM 的判断力，可能漏记或记错；建议观察 `/gamem` 的实际输出再调提示词
- 只按「群」隔离，**不区分同一个人在不同群的画像**（这是刻意的：避免 A 群记忆漏到 B 群）
- 事实是纯文本，没有结构化的置信度与来源引用

## 6. L4：群公共知识库（v0.6.0 新增）

L3 管「人」，L4 管「事」。群里沉淀出的**非个人**长期知识 —— 梗、约定、
共同经历、反复讨论得出的结论 —— 语义检索比结构化 KV 更合适（提问措辞
千变万化，精确匹配没意义），所以走 AstrBot 内置 FAISS + 本机 bge-m3。

### 6.1 写入（自动学习）

窗口休眠后的提炼**共用同一次 LLM 调用**：`kb_extract_appendix` 拼进
`l3_extract_prompt`（插在「# 群聊记录」小节之前），模型在同一份 JSON 里
多输出一个 `knowledge` 键。解析后经三道闸门写入：

1. **语义查重**：写入前拿候选文本与库里已有知识比相似度，最高值 ≥ `kb_dedup_score`（0.90）→ 跳过。
   阈值是实测校准的（2026-10-08，bge-m3）：「同一件事换个说法」0.92~0.93；
   「措辞相近的不同事」（如「小泽布尔是管理员」vs「…是群主」）≤0.77 —— 分界干净。
   ⚠️ **相似度必须插件自算**（`_embed` + `_cos`，按文本缓存）：AstrBot 的两套分数
   都不能跟固定阈值比 —— ① 底层 vec_db 是 `1 - L2²/2`，而 Ollama 向量**未归一化**
   （模长 25.7），原始分是负几百；② 融合分是 min-max **相对分**，库里只有一两条时
   任何查询都归一化成 ~1.0 → 查重必中、注入门槛（`kb_min_score=0.35`）形同虚设。
   实测事故：手动 `/garemember` 全被误判「已存在」回「没有写入」。
2. **每日额度**：`kb_daily_limit`（20 条/天），计数文件 `kb_usage.json`（与搜索额度同款）
3. **每群一库**：`群聊记忆-<群id>`，惰性创建 —— 没有知识流入就不建库

`remember()` 返回 **(写入条数, 说明文本)**：说明文本会直接回给 `/garemember` 的
使用者（「已记住 N 条」／「库里已经有了（相似度 93%）」／「今日额度用完」…）——
最早统一回「没有写入（可能是…）」，实测让用户把「查重跳过」误当成功能坏了。

写入用 `upload_document(pre_chunked_text=[...])`：一条知识 = 一个文档 =
一个 chunk，不经过文件解析器。**日期直接拼进正文**（`（记于 2026-10-08）原文`）：
嵌入时一起进去，检索命中后模型能看到记录时间，久远的条目自行打折扣 ——
知识有时效性，「最近大家在追 X」过俩月就不是事实了。

### 6.2 读取（检索注入）

`on_llm_request` 里用**当前消息**做 query 检索本群库，score ≥
`kb_min_score`（0.35）的 top3 注入 system_prompt（带 `kb_header` 表头）。
检索失败静默跳过 —— 知识库是锦上添花，不能挡回复。

**为什么不用 AstrBot 的 `kb_agentic_mode` 工具检索**：那会让每条回复多一轮
「模型决定调工具 → 工具返回 → 模型总结」的往返（约 +3s）。插件直查直注，
与 L1/L3 同款模式。

**预取**：检索实测要 0.8~1.8s（bge-m3 在 CPU 上做嵌入，不是当初以为的几十 ms）。
若等 `on_llm_request` 才查，这段时间全串行进回复延迟。现在 `on_group_message`
一放行就后台开跑（`_kb_prefetch`），到注入时通常已完成 —— 完全藏进管线时间。
预取对不上号（消息排队/合并）时退回当场查，行为不变。

### 6.3 调试与清理

| 命令 | 作用 |
|---|---|
| `/gakb` | 查看本群知识库概况（总条数 + 最近文档） |
| `/gakbforget` | 清空本群知识库（保留库本身） |
| `/garemember <内容>` | 手动写入一条知识 |

### 6.4 局限

- 提炼质量依赖 LLM 判断力；查重阈值 0.90 未在大量数据上校准（宁可多存，不丢信息）
- 检索注入与 L1 一样会破坏前缀缓存（见 §3.4）
- 未做过端到端真实数据验证（见 `roadmap.md` P0）

## 7. 窗口与记忆是解耦的

这是关键设计，别搞混：

| | 窗口 | L1 |
|---|---|---|
| 管什么 | **是否放行默认 LLM**（说不说话） | **记什么、注入什么**（懂不懂语境） |
| 生命周期 | 内存态，10s 滑动，最长 120s，到期即 SLEEP | 常驻，一直滚动 |
| 关系 | 窗口**开**时：放行 LLM **且** 注入 L1｜窗口**关**时：不注入、不放行，但**照记** | — |

好处：休眠不会让机器人"忘掉群里刚发生的事"，下次被 @ 时仍然接得上话。

## 9. 成本

| 项 | 估算 |
|---|---|
| L1 注入 | 25 条中文短句 ≈ **0.5–1k token / 次** |
| 触发频率 | 每条被放行的消息（@ + 窗口内消息）各一次 |
| 成本大头 | **不是 L1 条数，而是「窗口内放行了多少次」** —— 窗口内每条消息都会触发一次 LLM 调用 |
| L4 写入 | **零额外 LLM 调用**（与 L3 共享同一次提炼调用）；嵌入走本机 Ollama，无 API 成本 |
| L4 读取 | 每条被放行的消息一次本地嵌入检索（~几十 ms，无 API 成本）；仅库非空时发生 |
| 可优化 | ① 把 L1 移到 `extra_user_content_parts` 以保住前缀缓存（见 §3.4）；② 缩短回复（同时也是降延迟的最有效手段） |

---

## 10. 局限（已知且未解决）

1. **无持久化**：L1 与窗口都是内存态，桥/AstrBot 重启即重置。
2. **无话题切分**：L1 是无差别滚动窗口，群里同时聊两个话题时会混在一起。
3. **图片只留占位**：图片本身由模型原生理解（桥解密 + base64 上报），但 L1 里只记
   `[图片]` —— 不复刻图像，历史图片不会随记忆反复进 token。
4. **语音不可理解**：统一记 `[语音]` 占位。
5. **前缀缓存被破坏**：见 §3.4。
6. **L4 提炼质量未验证**：写入与检索链路已实现，但还没在真实群聊里跑过数据（见 §6.4）。
